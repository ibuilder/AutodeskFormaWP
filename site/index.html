Autodesk Forma → WordPress

Publish Forma projects to WordPress, safely.

A source-driven publishing workflow. Autodesk credentials stay in a backend you control, WordPress receives signed snapshots, and your public site never depends on a third-party API at request time.

Why not read Autodesk on every page load?

The obvious design — a WordPress plugin that queries Autodesk when a visitor arrives — fails on three counts. This project inverts the flow instead.

Credentials

OAuth access and refresh tokens in WordPress means tokens reachable by any compromised theme, plugin or admin session. Here they never leave the backend, encrypted at rest.

Availability

A marketing site would inherit Autodesk's uptime and rate limits on every page view. Published pages render from local content, so an upstream outage changes nothing.

Coupling

Rendering straight from upstream response shapes means a field rename becomes a broken public page. Everything is normalized into a versioned canonical schema first.

How it fits together

Three components, one direction of travel. WordPress never calls Autodesk.

What you get

Signed ingest

HMAC-SHA256 over method, route, timestamp, nonce and a hash of the body. Stale requests, replays and floods are all rejected.

Idempotent publishing

Projects match on their Autodesk source ID. Republishing identical content is recorded as skipped rather than rewriting the page.

Local edit protection

If an editor improves a page, the next sync will not silently discard that work. Hold it for review, keep the local version, or overwrite.

Blocks and shortcodes

Four server-rendered blocks and four matching shortcodes for project lists, single projects, metrics and assets — with theme template overrides.

Publishing templates

Pre-mapped views decide what actually reaches WordPress. A sustainability page cannot start leaking area metrics because upstream data changed.

Audit trail

Every publish, update, unpublish and archive is recorded with its result and connection. No IP addresses, no payload bodies, no secrets.

Quick start

Three pieces. The plugin is installable today; the backend needs an Autodesk Platform Services application.

  1. Install the WordPress plugin

    Upload the release archive on the Plugins screen, activate it, then open Forma → Connections and create a connection. The shared secret is shown once.

    define( 'FORMA_PUBLISHER_CONNECTIONS', array(
	'fp_yourkeyid' => 'your-shared-secret',
) );

  2. Run the backend

    It holds every Autodesk credential and does all the talking.

    cd backend
cp .env.example .env
npm install && npm run build && npm start

  3. Check the whole pipeline

    Exercises configuration, the Autodesk session, project access, payload assembly and a signed round trip to WordPress. Publishes nothing.

    npm run verify

Security model

WordPress holds no Autodesk credential. Not by policy — by construction. The plugin has no Autodesk client, no token storage and no code path that reaches developer.api.autodesk.com.

Failed authentication is charged to the origin address and only verified requests count against a connection, so learning a key ID cannot be used to lock the real backend out. Remote media import is off by default and, when enabled, restricted to an explicit host allow list.
